# Research Method

## 1. 연구 목적

이 연구는 공방전 당시의 사실을 바꾸지 않으면서, 사후 분석 과정에서 발생한 triage 병목을 AI 보조 파이프라인으로 얼마나 줄일 수 있는지 평가합니다. “AI가 취약점을 찾았다”는 주장보다 다음 질문에 답하는 것을 목표로 합니다.

- **RQ1:** Semgrep 단독 대비 여러 분석기 결과를 통합하면 검토 누락이 얼마나 줄어드는가?
- **RQ2:** 정적 결과에 패치 diff와 격리 실행 증거를 연결하면 오탐 triage가 빨라지는가?
- **RQ3:** AI 보조 설명·그룹화가 사람의 판정을 바꾸지 않으면서 검토 시간을 단축하는가?
- **RQ4:** 생성된 회귀 테스트가 패치 제거 또는 우회 변형을 다시 탐지할 수 있는가?

## 2. 시간 순서에 따른 연구 단계

### 2.1 개요

BoB 15기 A&D의 대상은 EDU, Fintech, Healthcare, Manufacturer 네 서비스였습니다. 작성자는 Manufacturer 방어를 담당했습니다. 보고서에는 팀 전체에서 공유된 증거와 작성자가 직접 수행한 작업을 구분하여 표시합니다.

### 2.2 공방전 전 전략 수립

사전에는 운영 원칙에 따라 Gamebox를 임의 설치하거나 문제 소스를 미리 분석하지 않았습니다. 제한 시간 중 빠르게 실행 가능한 Semgrep을 주 분석기로 선정하고, 호출 관계와 데이터 흐름의 심층 확인이 필요한 후보는 CodeQL로 보조하는 전략을 세웠습니다. 실제 CodeQL 실행은 고사양 교실 데스크톱을 사용하는 지정 팀원이 담당하도록 역할을 분리했습니다.

### 2.3 공방전 실제 진행

#### 2.3.1 취약점 탐색

실전에서는 Semgrep 결과, 서비스 설정, HTTP 응답과 로그를 함께 검토했습니다. 사례별 결과는 성공·실패·불확정으로 나누어 기록하며, 공개 허가가 확인되지 않은 서비스별 취약점 유형·경로·입력값은 이 저장소에서 다루지 않습니다. 단순 HTTP 상태 코드만으로 성공이나 안전을 확정하지 않습니다.

#### 2.3.2 패치로부터 취약점 추론

공방전 중 적용된 패치는 단순 결과물이 아니라 결함 위치를 찾는 단서로 취급했습니다. 인증 guard 추가, endpoint 비활성화, sink 교체, 허용 목록 추가와 같은 diff에서 원래 누락된 보안 조건을 추론하고, 소스의 입력점과 sink를 역방향으로 확인했습니다. 다만 패치가 있었다는 사실만으로 취약점을 확정하지 않고, 해당 코드 경로와 실행 가능성을 별도 검증 대상으로 두었습니다.

### 2.4 공방전 후 분석 및 검증

#### 2.4.1 배포 호스트 소스 분석

공방전 이후 확보가 허용된 배포 호스트 범위에서 소스·설정·의존성을 다시 검토했습니다. 이 단계는 당시 실전 탐지와 분리해 기록하며, 원본 Gamebox 자료를 공개 저장소에 복제하지 않습니다.

#### 2.4.2 기존 SAST 활용

Semgrep과 CodeQL 등 기존 분석기 결과를 수집하고, 중복·비도달 경로·설정 의존 항목을 사람이 triage했습니다. 사후 1차 분석에서 197개 항목을 정리했습니다. 이 값은 자동 분석과 수동 검토 과정의 후보 수이며 독립적인 확정 취약점 수가 아닙니다.

#### 2.4.3 사용자 정의 분석 도구

본 저장소의 AI 보조 SAST는 이 시점 이후 시작한 후속 연구입니다. 기존 도구의 SARIF를 공통 schema로 정규화하고, endpoint·데이터 흐름·패치 diff·격리 실행 결과를 연결하여 검토자가 근거를 한곳에서 확인하도록 설계합니다. AI는 중복 그룹화, 근본 원인 가설, 추가 검증과 회귀 테스트를 제안하지만 취약점을 자동 확정하지 않습니다.

#### 2.4.4 생성 payload 검증

AI 또는 규칙에서 제안된 테스트 입력은 개인 소유의 격리 서버에 배치한 허가된 문제 파일 또는 synthetic 변형에만 적용합니다. 정상 동작을 파괴하지 않는 canary를 사용하고, 패치 전 성공·패치 후 차단·정상 기능 유지 여부를 함께 확인합니다. 이 동적 검증 및 패치 우회 관점에서 44개 항목을 추가 정리하여 전체 연구 후보는 241개가 되었습니다.

## 3. 데이터셋과 라벨

전체 241개 후보의 심각도 분포는 다음과 같습니다.

| 출처 | 후보 수 | 의미 |
| --- | ---: | --- |
| 사후 1차 소스·기존 SAST 분석 | 197 | 소스·설정·분석기 결과를 정리한 항목 |
| 개인 서버 동적·패치 우회 검증 | 44 | 격리 검증에서 추가 정리한 항목 |
| 합계 | 241 | 확정 취약점 수가 아닌 전체 연구 후보 |

| 심각도 | 후보 수 | 비율 |
| --- | ---: | ---: |
| Critical | 24 | 9.96% |
| High | 89 | 36.93% |
| Medium | 109 | 45.23% |
| Low | 19 | 7.88% |
| 합계 | 241 | 100.00% |

각 후보에는 심각도와 별도로 다음 상태 중 하나를 부여합니다.

- `candidate`: 분석기가 탐지했으나 아직 검토하지 않은 항목
- `evidence_supported`: 정적 경로, 설정 또는 patch 근거가 연결된 항목
- `sandbox_reproduced`: 허가된 격리 환경에서 재현한 항목
- `reviewed_confirmed`: 사람이 근본 원인과 영향을 검토한 항목
- `rejected`: 오탐, 중복 또는 비도달 경로로 판정한 항목

실전에서 확인한 사례, 사후 발견 항목, synthetic mutation을 서로 다른 dataset split으로 유지합니다. AI 프롬프트에 정답 label이나 실제 payload를 노출한 자료는 blind discovery 평가에서 제외합니다.

## 4. 비교 실험

다음 조건을 동일한 held-out fixture에 적용합니다.

| 조건 | 구성 | 확인 목적 |
| --- | --- | --- |
| B0 | Semgrep 기본·사용자 규칙 | 빠른 분석 기준선 |
| B1 | CodeQL 결과 | 심층 흐름 기준선 |
| B2 | Semgrep + CodeQL 정규화 | 단순 도구 통합 효과 |
| B3 | B2 + AI triage | 설명·중복 제거 효과 |
| B4 | B3 + 패치·격리 증거 | 증거 연결 효과 |

CodeQL을 실행할 수 없는 환경에서는 해당 조건을 `not available`로 표시하고 Semgrep 결과로 대체한 것처럼 작성하지 않습니다. 각 실험은 동일 commit, 규칙 버전, 제한 시간과 자원 조건을 기록합니다.

## 5. 평가 지표

- Precision, Recall, F1 및 심각도별 Recall
- Top-5와 Top-10 후보 내 confirmed finding 비율
- 중복 경고 감소율과 root-cause group 수
- 후보 한 건당 triage 시간 및 전체 검토 시간
- AI 제안 수락·수정·기각 비율
- 존재하지 않는 파일·함수·줄 인용 비율
- 패치 후 동일 공격 차단율
- 정상 기능 회귀 테스트 통과율
- 패치 우회 mutation 재탐지율
- 분석 시간, peak memory, AI token 및 비용

사람 검토 시간은 최소 두 번 반복하여 학습 효과를 기록합니다. 가능하면 후보 순서를 무작위화하고, 검토자가 어떤 조건의 결과인지 모르게 하여 AI 출력에 대한 기대 편향을 줄입니다.

## 6. 패치 검증 기준

패치는 다음 조건을 모두 만족할 때만 유효한 수정으로 기록합니다.

1. 빌드와 기존 기능 테스트가 통과합니다.
2. 정적 분석 경고 또는 근본 원인이 제거됩니다.
3. 동일한 canary 기반 재현이 차단됩니다.
4. 허용된 정상 입력은 계속 동작합니다.
5. 단순 encoding, 필드명 변경 또는 대체 endpoint를 이용한 held-out mutation에도 같은 보안 조건이 유지됩니다.

정적 경고만 사라진 수정은 sink 숨김이나 rule 회피일 수 있으므로 완료로 판정하지 않습니다.

## 7. 생성 테스트의 안전 통제

생성 payload는 실행 가능한 공격 문자열이 아니라 먼저 구조화된 test intent로 저장합니다. 예를 들어 “shell metacharacter가 포함된 입력이 프로세스 실행에 도달하지 않아야 한다”는 조건을 생성하고, 실제 입력은 synthetic fixture에 맞춰 제한적으로 구성합니다.

- 외부 IP·domain 및 실제 계정 사용 금지
- DNS·HTTP egress 기본 차단
- canary 파일과 synthetic secret만 사용
- 원본 flag 및 운영 token 복사 금지
- 시간·메모리·프로세스·파일 크기 제한
- 사람이 승인한 test case만 실행
- 실패, 무응답 및 불확정 결과도 그대로 보존

## 8. 타당성 위협과 한계

서비스별 언어·프레임워크 차이로 분석기의 coverage가 다릅니다. 실전 중 확인된 소수 사례를 중심으로 규칙을 만들면 과적합될 수 있으며, patch diff를 제공하면 답이 유출될 수 있습니다. 이를 줄이기 위해 route·변수명·호출 구조를 바꾼 held-out mutation과 안전한 negative fixture를 함께 사용합니다.

241개 후보는 자동 탐지와 서로 다른 검증 단계에서 수집되었으므로 동일 수준의 ground truth가 아닙니다. 따라서 수량 자체를 성능으로 사용하지 않고, 상태별 분포와 사람이 확정·기각한 비율을 함께 보고해야 합니다. 또한 개인 서버 재현 결과는 당시 공방전 네트워크·배포 환경과 완전히 같지 않으므로 외적 타당성에 한계가 있습니다.

## 9. 공개·재현 원칙

공개 artifact에는 synthetic fixture, 일반화한 규칙, aggregate metric과 민감정보를 제거한 schema만 남깁니다. 원본 문제 소스, 실제 payload, flag 및 운영 인프라 식별자는 공개하지 않습니다. 공개 데모 결과와 비공개 실험 결과를 별도 디렉터리와 별도 provenance로 관리하며, 보고서의 모든 표에는 데이터 출처와 확정 상태를 명시합니다.

## 10. 보고서용 요약 문단

> 공방전 당시에는 Gamebox를 사전에 설치하지 않는 원칙 아래 Semgrep을 중심으로 빠른 코드 패턴 탐색을 수행하였고, CodeQL은 고사양 교실 데스크톱에서 지정 팀원이 보조적으로 실행하였다. 실전 사례는 성공·실패·불확정 상태를 구분해 기록하되, 공개본에서는 서비스별 세부 내용을 제외하였다. 공방전 후에는 배포 호스트 소스와 기존 SAST 결과를 재검토하여 197개 후보를 정리했고, 개인 서버의 격리 환경에서 동적 검증과 패치 우회 관점의 분석을 수행하여 44개 후보를 추가하였다. 총 241개 후보는 Critical 24개, High 89개, Medium 109개, Low 19개로 분류되지만, 이 수치를 모두 독립적인 확정 취약점으로 해석하지 않고 증거 수준과 수동 검토 상태를 별도로 관리하였다. 이러한 사후 분석의 triage 병목을 개선하기 위한 향후 과제로, Semgrep·CodeQL 결과와 패치·실행 증거를 통합하고 AI가 설명과 검증 계획을 보조하는 사용자 정의 SAST 프로토타입을 설계하였다.
